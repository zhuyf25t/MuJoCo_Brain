## 第二轮为何慢

整轮耗时约 92 秒，其中 47 次模型调用合计等待约 80.06 秒；API 报告总 token 用量为 70,036（不是费用估算）。

| 模块 | 调用次数 | API 等待秒数 |
| --- | ---: | ---: |
| `analyze_reach` | 1 | 4.594 |
| `analyze_motion` | 7 | 13.593 |
| `find_ball` | 8 | 12.236 |
| `match_grasp` | 16 | 25.295 |
| `plan_motion` | 15 | 24.342 |

前进只有三次：`0.2s + 0.4s + 0.4s = 1.0s`，此外有四次 `0.2s` 转向。旧配置将正式动作时长也限制为最多 `0.6s`，每走一小段又重复申请资料并询问模型，因此主要问题是小步和调用间隔，而非调低了底盘速度。

操作经验确实进入了模型输入：包括同一动作的前图、后图、实际工具名及秒数、分析文字。第二轮最后一次 `plan_motion` 就收到了一组右转两图和 `turn_right(0.2)`；模型仍要求更细的同类资料。运动分析出现过“前后基本不变”，范围与左右方向的解释也有矛盾，不能将这些文字直接当作可靠速度标定。

## 已修正并做本地验证的行为

- 保存 reach 原图及分析，即使候选区域不确定也回到 stow；后续匹配负责判断是否足够可靠。
- 重复申请已有资料时告知“这些是全部现有样本”，允许据此判断或返回 unknown，仍保留有界请求次数。
- 匹配必需的 reach 资料由阶段代码申请；刚学到的同方向运动资料直接提供给规划模块，避免重复索取。
- 首次空库试探仍是 `0.2s`，正式动作默认上限改为 `2.0s`，要求根据图像变化及当前远近选择时长。
- 程序为有效运动样本补充 `image_rate`，将参照物的归一化坐标差除以实际秒数，与原图一起交给规划模块；该值仍依赖定位质量，不当作真实米/秒。
- 连续同方向移动的测试场景中，每帧调用分析、定位、匹配和规划各一次；换方向需要更多资料时仍可增加调用。

本地回归测试：**71 项通过**，包括模块输入隔离、五阶段、资料权限、三态持球、最终检查、程序替换、重复申请、运动图像变化率和较长正式动作。第二轮之后的这些优化尚未用第三轮 GUI 验证；当前没有新 brain 完成抓球投箱的成功实跑证据。
