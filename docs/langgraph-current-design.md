# 当前 LangGraph 到底在做什么，以及怎样让较低 reasoning 的模型更容易完成任务

核对日期：2026-09-27。代码基准：`goal_langgraph` 的 `cdd5d2f155cd7bd4ed071cff155f3e9509c10da7`。

这份文档说明已经实现的系统，并评估下一步的选择。文中的改进建议尚未实现、尚未跑新的模型实验。不能把建议当成现有能力，也不能把一次入箱成功当成稳定成功率。

## 1. 先回答几个最容易混淆的问题

**当前没有把前几轮的 reasoning 原文塞回模型。** 每次请求重新构造 system 和 user 消息。传回去的是挑选过的照片、程序保存的状态，以及模型公开输出的简短理由、预期、经验和失败分析。`reason` 是我们要求模型填写的操作说明，不是 API 的 `reasoning_content`。

**当前已经有信息提取，但没有专职的上下文总结模型。** 观察请求把照片变成物体与空间关系描述；规划请求填写 `learning`、`review`、`motion_effect` 等字段；程序挑选、覆盖或截断这些内容。没有另一位“文字秘书”重新审阅整个历史、合并矛盾、产出经过核对的短摘要。

**当前有多个模型调用角色，但都调用同一份模型配置。** 观察、夹爪复核、规划共用同一个 `OpenAICompatBrain` 请求接口与 thinking 设置。把全局配置设成 high，不会自动变成“便宜模型看图、强模型思考”。

**当前 LangGraph 的流程部分很接近一个带持久状态的有限状态机。** 三个任务节点都调用同一个规划函数。它的价值来自我们写进去的记忆、反馈与检查；框架本身不会帮我们发现失败原因、压缩上下文或提高视觉准确率。

**low 或关闭 thinking 值得尝试，但目前没有证据保证成功。** 需要判断和比较，并不等于每次必须开启长时间的显式 thinking。反过来，当前版本开 high 后成功过一次，也不能证明高 reasoning 足以稳定完成任务。

## 2. 一轮、一个 episode、一个动作分别是什么

一个 episode 是一次完整的“从开始到尝试把任意一颗球放进箱子”的任务。当前上限是 **32 次看图决策**，不是 32 条动作，也不是 32 次 API 请求。

一轮的过程是：拍当前车头图，让 brain 决定接下来一整批动作，然后由采集程序按顺序执行这批动作。执行结束后，下一轮才会把新照片交给 brain。

例如，一批可以是“抬肩、左转、向前走、降肩”。模型预测的是这整段的效果，不是只预测一个关节的小动作。一个阶段可以持续数轮；一轮也可以在看清上一批结果后，直接开始下一阶段的工作。

**一批动作中途没有新的模型判断。** 把一段前进拆成三条短 `forward`，再放进同一批，不会增加纠错机会。把 `observe` 放在批次中间，也不会让模型在那里重新看图；这个工具只让底盘停下、让环境走两个控制拍。要根据新图改变计划，就必须结束当前批次。

记录器会保存动作中间的图片和控制轨迹，但这不表示模型当时看过这些图片。模型只能依据实际送入请求的图作决定。

## 3. 模型能看到什么，哪些信息故意不给它

允许的输入是当前车头 RGB、被选中的历史车头 RGB、任务、公开工具说明、自己下发过的动作名和参数，以及这些信息形成的记忆。

不发送仿真中的实际关节角、机器人和球的真实位置、TCP 坐标、程序测距、持球传感器、工具的 `ok/result`、俯视图和侧视图。Python 层的 observation 和本地日志可能有这些字段；模型请求出口会筛掉它们。

这使策略将来有机会迁移到只有车头相机和动作接口的真机。代价是：发过“合爪”只说明下发过命令，不能证明真的夹到球；发过肩关节增量不能证明末端移动了预期距离。实际效果仍要看新图。

绿色或黄绿色圆球是目标球，洋红色物体是箱子。机械臂的棕色关节、横掌、两块夹指和它们的地面影子要分开辨认。相机固定在车头，抬臂不会把相机抬高。

最终是否成功由环境独立判定。环境用于评估的真值可以在本地分析中查看，但不能回填成 brain 的观察依据。

## 4. 三个阶段，用实际目的来解释

### 4.1 探索：先学会一套可以重复使用的抓球方法

目的不是把规定动作执行三遍，也不是认识场景里的所有物体。目的是弄清楚：**爪放到什么姿态可以尝试夹地上的球；怎样抬开视线；怎样回到刚才的姿态。**

先在照片里辨认小臂末端连接的横掌和两块实体夹指，确认开口在哪里。仅看见圆关节或地面影子不够。如果夹指不在视野里，可以用一个预设姿态把它带到前方，再看新图。预设名字叫 `reach`，并不保证它已经适合抓球。

接下来找到一个候选低位：两块夹指大致朝下，张开的空间能够从左右包住地面上的球。肩和肘在这一段都可以调整。用户说的“撑到地上、相对竖着”，表达的是夹指应当下降到能夹住地面球的高度；实现中不把压住地板当成必要条件，因为球有高度，指尖可以略微离地。

不知道关节方向时，尝试必须有明确的问题。例如：“保持车和肘不动，只改变一次肩，比较调整前后同一块指尖与地面的关系。”这次试验回答的是该肩动作造成了什么变化。若肩肘和车同时动，就只能判断组合效果，不能给其中一个动作单独建立方向经验。连续两张图几乎不变，也不能自动推出已经到底，可能受限，也可能看不清。

保存候选低位照片后，固定肘，只动肩，把机械臂移开找球和开车需要的中央视线。不是只要能从机械臂两侧看见球就合格；球对到车头正前方时也要能继续看见。空爪可以部分甚至全部离开画面。

然后验证从这个就绪位能否靠肩返回低位。保存“低位照片、就绪照片、去程肩动作、回程肩动作”。两个方向都要有结束后的照片支持，不能仅把去程数值取反，就当回程已经验证。

这仍只验证了姿态能往返，没有证明一定抓得住。球应该放到图片哪个区域，最初只是从空爪估出的候选；需要实际把球送到低位爪口附近，再检验球与两块实体夹指的关系。

约 3–5 轮只是预算希望。当前没有到了第 5 轮强制结束探索的规则，因此错误的夹爪识别或反复无效动作可能耗尽整个 episode。

### 4.2 捡球：把同一颗球送进两块夹指之间，再验证是否抓起

先使用就绪位看球和看路，选一颗容易接近的球。让车转向、接近，把球送到夹口会落下的位置。左右方向通常接近画面的水平中央；前后位置要看低位爪和地面球的关系，不能机械追求整张图片的正中心。

球远、通路清楚时，可以预测较长的一段接近动作。球近后，一样长的前进时间会造成更大的画面变化，且可能推到球，因此要在还来得及纠正的地方结束批次。上次前进一秒的画面变化不是恒定速度标尺。

首次抓球，或已确认抓空后，当前提示要求先结束在“球与低位张开的夹指同图”的位置，下一轮看清对位再决定合爪。这样避免仅凭一个猜测出来的框，把接近、下降、盲闭爪全部连做。

看清球在实体夹指内侧之间后，可以同批闭爪、抬肩。抬起既要让球离地，也要让下一张图还能辨认球和夹指的接触。空爪找球时可以完全抬出画面；抓完检查时完全出画，会失去结果证据。

下一张图有三种结论：看清夹着球且离地，进入投放；看清指间为空，修正抓取；被挡住或出画，先改善观察，保持可能已有的夹持。

抓空后的正确思路是：“上次希望夹住，实际空了；现有照片支持哪一类偏差；下一批改变什么；下一张图怎样检查改变是否有用。”失败本身不能说明一定太远或太近。恢复就绪只解决看路和看球，不会自动修正车距；原样抬起、降下、闭爪，通常会重现原结果。

### 4.3 投放：把球送到箱口内侧，再给它向下落的空间

保持夹持，找到洋红箱子并接近。需要同时满足：球能越过近侧箱沿，落点在开口内部，并且还能看见足够的球和夹指接触来判断结果。

球在图上与箱子重叠不等于球已到箱内。要区分近侧外壁、箱沿、内部开口，以及到底是谁遮住谁，并比较接近或调臂前后的照片。仅转向不能证明前后距离正确。

可以把有把握的调臂、转向、接近放在同一批，但**最后一次定位与松爪之间必须取得新图**。目前这部分既有提示要求，也有代码检查；不是模型写一句“应该可以”就能放行。

松爪后检查球实际去了哪里。球还卡在沿上或夹块附近，就要分析支撑、挤压和遮挡，不能重复张爪并假定已经下落。球掉到地上则重新捡；如果投放中改过肘，原来的固定肘抓法需要先恢复或重新建立。

环境也可能在松爪后的批次末尾直接判定成功并结束 episode；成功那次就是这样结束的，不一定再多一轮让模型返回 `done(true)`。

## 5. 真正的图很小，模型调用藏在节点里面

当前代码的图是：

```text
每轮 START
    │
    ├─ 上轮 phase = explore → explore ─┐
    ├─ 上轮 phase = pick    → pick    ─┼→ END → 把动作交回 run_collect
    └─ 上轮 phase = place   → place   ─┘

三个节点内部都调用 _plan；本次图运行到此结束。
run_collect 执行动作 → 拍下一张图 → 下一轮重新 START。
```

没有一条图内的 `explore → pick → place` 执行动作链。阶段变化写在状态的 `phase` 中，下一轮按它选择入口。这是为了防止在没有新照片的情况下，仅靠换节点就假装机器人已完成动作。

本轮如果看清上一批已经抓到球，可以从 `pick` 入口直接输出 `phase=place` 和运输动作，不需要再调用一遍 place 节点。规划提示每次包含所有三个阶段的说明，正是为了允许这种切换；同时，这也是当前提示很长的原因。

一次 `_plan` 的实际工作如下：

| 工作 | 输入与目的 | 是否另发模型请求 |
| --- | --- | --- |
| 对账上一批 | 检查动作历史是否与上轮返回的完整批次一致；不读取执行成功标记 | 否 |
| 当前图观察 | 只看当前照片，描述球、实体夹爪、持球与释放关系；不看旧计划，减少顺着预期解释图片 | 是；图片完全相同时可复用缓存 |
| 首次抓取前的夹爪复核 | 加上本车夹爪外观说明；按条件带候选参考和上一批前图，帮助分辨实体、影子及姿态变化 | 条件满足才调用，同样可缓存 |
| 规划与记忆更新 | 读当前图、选中的历史图、观察描述和状态，分析上一批，再输出下一批及状态更新 | 是 |
| 格式和行为检查 | 检查字段、参数、参考资格、阶段条件、释放条件等 | 否 |
| 不合格计划修正 | 反馈检查错误，用相同观测重新规划；没有执行第一份计划 | 最多追加一次规划请求 |
| 保存和返回 | 写入 checkpoint 与诊断日志，返回有序动作批次 | 否 |

所以正常一轮常有 2 次请求，符合夹爪复核条件时常有 3 次，规划重试还会增加。观察格式不合格时可能直接返回 `observe`，不进行本轮规划。

成功那次第 3 轮是一个具体例子：第 06 次 API 请求只观察当前图，第 07 次复核夹爪并比较前后图，第 08 次结合状态和上述描述进行规划。这三次之间机器人没有执行新动作；规划通过检查后，采集程序才执行返回的动作批次。阅读包按 API 请求编号，所以同一轮会出现多条记录。

`run_collect` 一轮只调用一次 `brain.decide()`；多次 DS 请求发生在 brain 内部。API 里的 `describe_scene`、`report_plan` 是让模型按指定结构回答的报告名称，不是机械臂动作。真正交给机器人执行的是规划结果里的 `actions`。成功那次的三个数量分别是 **22 轮决策、56 次模型请求、41 条机器人动作**。

“首次抓取前复核”有具体限制：入口为 explore/pick，没有已知持球，当前观察也没报 held，历史中已经张过爪、但从未闭过爪。它不是每次失败后都重新调用的全能复核员。复核主要替换规划输入的夹爪形态描述，不替换基础观察的 holding 和释放判断。

## 6. 状态里到底存了什么

状态不是聊天全文，也不是所有仿真观测。持久状态只有下面七个顶层字段，但其中的自然语言内容仍然可能冗长或判断错误。

| 字段 | 用人话解释 | 保留和失效方式 |
| --- | --- | --- |
| `phase` | 下一轮默认从探索、捡球还是投放开始 | 由规划报告更新，受部分阶段条件检查 |
| `calibration` | 抓球方法的笔记：低位照片及估计区域、就绪照片、两个方向的肩动作和最近经验 | `lessons` 仅留最近 4 条；保存新低位会重置旧就绪与往返；改肘或预设使往返失效 |
| `arm_anchor` | 最近一次从图中认出的低位或就绪位，以及当时照片 | 用于把两个确认过的端点之间的肩动作绑定起来；不是当前关节角 |
| `visual_memory` | 最近目标记录，以及最近一张支持持球的照片 | 旧目标不代表当前仍看见；明确 empty 会清除持球记忆，unclear 不会自动清除 |
| `last_batch` | 上批前图、动作、为什么这样做、希望下一图怎样，以及当时对更早一批的评价 | 每轮覆盖为刚发出的批次；动作是已下发指令，预期不是结果 |
| `correction` | 一个尚未解决的问题：原始偏差、原因假设和最初前后图 | 问题存在时保留原始问题，更新假设；模型报告 resolved 才清除，不存一串问题队列 |
| `motion_example` | 最近一次能对应同一目标的前进/后退经验：前后图和观察到的效果 | 新的有效样本覆盖旧样本；只在相同阶段提供作参照，不是速度模型 |

照片引用保存 `image_id` 和当时已经下发的动作数 `history_n`。图片本体存在本地数据库和诊断目录；这两个字段使“这张前图与那张后图之间到底下发了哪些动作”可以由程序精确关联，不让模型编写历史。

这里的“确认”通常仍是模型基于照片的判断，不是程序做了可靠三维测量。程序能证明某几条肩指令位于两张参考图之间，不能证明模型选中的两张图真是正确的低位与就绪位。

当前也没有一个永久的“这套抓法已经成功过”的单独字段。`held` 保留的是最近持球证据，后面明确空爪时会清除；提示里说可以复用成功经验，比结构化状态里实际保留的成功技能信息更丰富。两者并不完全对齐。

## 7. 下一轮实际会收到哪些历史

程序会选取上批前图、未解决问题的前后图、同阶段运动经验的前后图、低位与就绪参考、最近持球证据、箱子目标参考，以及当前图。重复图片去重，历史按时间排序，当前图放最后并明确标记。投放阶段省去姿态参考图；旧的球目标图不会单独作为当前球位置参考发送。

文字包括完整的状态投影、最近最多 12 条动作名和参数，以及修正样本和运动样本两张图之间的完整动作序列。即使一组样本较早，它对应的动作也不靠“最近 12 条”猜测。

这是**按用途选取记忆**，并非把所有历史裁到固定 token 长度。`learning` 最近四条是截断，也不是语义总结。`reason`、`expected`、`review` 等有非空要求，但大多没有代码层面的严格长度预算。

我们离线检查了成功 episode 的全部 56 次请求：每次都是新构造的 system、user 两条消息，没有历史 assistant 消息，也没有 `reasoning_content` 字段。`rounds.jsonl` 保存公开的工具调用或回答内容、用量与耗时，没有保存隐藏 reasoning 原文。下一轮也不会把整个日志读回去。

因此，现在要解决的不是“找一个模型压缩长篇原始 reasoning”。更准确的问题是：**应该让谁从照片和动作结果里提取什么信息，哪些信息值得保留，怎样避免旧的错误结论压过新的证据。**

## 8. SQLite 做什么，以及没有做什么

默认文件是 `brains/langgraph_temporary_file.sqlite`，使用固定 thread ID `main`。这里的 `main` 是 LangGraph 线程名，与 Git 的 main 分支无关。

同一 episode 中，checkpointer 保存各轮图状态，图片表保存图像。文件不会因为一轮结束或进程退出自动消失；这也不意味着重新启动就会自动接着上次任务干。

采集程序每个 episode 调用 `reset()`；第一轮要求空 `history=[]`，然后清除这个线程的旧 checkpoint 和数据库中的图片，建立新的 episode 记忆。它不是每次看到 history 为空就无条件清库，也不接受把 `history=None` 当成新集入口。

历史诊断文件留在 `data/langgraph_runs/时间戳/`，新 episode 不会把这些日志目录删掉。它们用于人看和离线分析，当前不会自动作为跨 episode 技能库检索。

数据库负责保存，不负责理解、压缩、纠错或学习。当前没有跨 episode 的可复用技能记忆，也没有从崩溃点恢复机器人真实状态的完整机制。

## 9. 哪些是硬检查，哪些只是提示里的要求

硬检查包括：工具名和参数合法；`done` 独占一批；同批闭爪后不能再松爪；进入 pick 前存在两份参考和双向肩动作；pick 不能改肘或用臂预设；捡球/投放需要评价上批；满足条件的前进后退必须报告效果；可能持球时，释放需要当前观察和历史定位证据满足条件。

一些关键要求主要靠提示执行，例如“影子不是实体夹爪”“抓空后要有相关变化才重试”“当前照片看不清就不要假装已对准”。代码没有一个独立、可靠的视觉算法来证明模型做到了这些要求。

例如，`review` 写了原因，并不保证原因是对的；`motion_effect` 写“几乎没动”，并不保证前后球真的没变大；保存 `grasp_reference` 并不证明这张图里真的有可抓球的实体夹爪。

自动测试主要验证协议、状态更新、输入边界及违规动作是否被拒绝。测试通过不能替代真实视觉闭环成功率。

## 11. 目前最值得正视的缺陷

**第一，错误的视觉判断会被升级成记忆。** `ep_0014` 曾把影子当成候选夹爪参考。后续再围绕这个参考判断高度和往返，数据库反而帮助错误延续。高 reasoning 的成功轨迹也出现过误认夹爪、错误估计运动效果。增加文字总结不一定修好这一点，可能把错误写得更像定论。

**第二，同一个规划请求承担太多事情。** 它既要重新看多张图，又要判断阶段、评价失败、估计动作幅度、维护多组状态，还要遵守复杂 JSON 协议。更小的推理预算未必有足够余量完成这些不同性质的工作。

**第三，记忆保留有机制，但缺少系统的证据等级与失效管理。** 已观察到的现象、原因猜测、成功验证过的技能，没有统一分层。已有部分失效规则，但没有完整的“这条经验在什么条件下可靠，出现什么反证就撤销”的结构。旧错结论不能仅靠多写一句“请核对”解决。

**第四，格式问题会打断物理反馈。** 成功轨迹有一次观察枚举多带引号，被拒后回退 `observe`；这个回退覆盖了尚未评价的后退批次，下一轮不再强制反馈那次后退。另有两次规划协议错误导致完整重规划。这些是实际记录的问题；并没有证据说它们单独导致了所有抓空。

这些缺陷说明系统还有改善空间，不说明增加节点就会更好。当前主要负担在感知、上下文组织和错误恢复，图上再画几条边不会直接解决。

## 12. 一个纯文字模型可以帮什么，不能帮什么

可以帮忙。合理的职责是读“新观察摘要、真实下发的指令、上次预期、已有记忆”，更新一份很短的任务记录：现在确认了什么、还不知道什么、刚才哪个假设被推翻、下一步需要检验什么。

例如下面这份记录，目标是帮助下一轮继续一个具体问题，而不是替模型写长篇思考：

```text
当前阶段：捡球。
照片中的现象：上轮合爪并抬肩后，指间清楚可见为空。
尚未解决：刚才的对位没有得到持球。
原因假设：球可能还在夹口远侧；高度是否合适尚未确定。
可复用经验：保留已核对的低位与就绪参考，不从头试方向。
下一批目的：看清原目标，检验前后距离这一项偏差。
下轮要检查：相同低位下，球与两块实体夹指的关系是否改善。
证据：这次失败前后图及其间下发的完整动作。
```

这是建议格式，不是一次真实轨迹的逐字摘录。动作数值应由对应记录取出，不由总结模型编造。照片中的现象也只是观察模型的报告，应该保留其来源与不确定性。

纯文字模型看不到照片本身。视觉模型若把影子说成夹爪、把不同的球说成同一颗，文字模型通常不能凭更漂亮的摘要找回丢掉的视觉信息。因此边界关系仍应能回看对应图片；只把所有图片永久转换成文字，会丢失关键细节。

还要区分“总结”和“规划”。总结负责把已发生的事情整理清楚，规划负责选择下一段动作。可以由同一个模型在一次结构化回答里完成，也可以分工；不是有 memory 就一定要另加一次 API 请求。

如果引入专职总结，建议先只在阶段切换、出现矛盾、连续没有进展或上下文超过预算时调用。摘要保留来源、未知和反证，不能把待验证假设压成事实。先测它减少了多少后续 token、增加了多少延迟和错误，再决定是否每轮使用。

LangGraph 官方提供通过状态里的 summary 和显式总结节点实现这种机制的示例。它需要我们编写并调用，不是接上 checkpointer 就自动获得。[官方记忆文档](https://docs.langchain.com/oss/python/langgraph/add-memory#summarize-messages)

## 13. 如何让 low 或关闭 thinking 更有机会做好

### 13.1 不把“需要判断”与“每次 high”混为一谈

关闭显式 thinking 不等于模型完全没有判断能力。这里需要的是看清关系、利用经验、检验失败原因；这些能力可以由模型、明确状态、稳定的控制方法共同承担。哪些步骤必须更多推理预算，需要实验回答。

当前 DeepSeek 接口里，thinking 的开关和 reasoning effort 是两个设置：本项目用 `thinking=enabled` 配合 `reasoning_effort=low/high`，用 `thinking=disabled` 关闭；不是把 `reasoning_effort` 填成 `disable`。[DeepSeek 官方说明](https://api-docs.deepseek.com/guides/thinking_mode/)

当前配置对所有角色一视同仁。若以后想观察用 low、复杂修正用 high，需要改成按调用角色或困难事件选择配置；现有代码还没实现。

### 13.2 先减少每次都要重新解决的问题

| 建议 | 具体做法 | 为什么可能有效；仍需验证什么 |
| --- | --- | --- |
| 按阶段组织提示 | 只给当前阶段的操作说明，以及进入/退出相邻阶段所需的简短条件 | 减少无关文字；要验证删减后是否遗漏关键边界 |
| 把记忆整理成证据明确的短记录 | 当前现象、已验证经验、未解决问题、原因假设、下一次检查分开；程序保留图片和动作来源 | 减少旧结论冒充当前事实；摘要仍可能出错 |
| 简化模型输出协议 | 自动可导出的身份、时间、图片绑定由代码完成，模型集中输出观察、动作目的、动作和必要更新 | 减少重复字段与整批重试；不能把真正的行为矛盾当格式问题放行 |
| 把参考与成功经验分开 | 区分“看起来可尝试的低位”与“实际闭爪抬起后确认过持球的抓法”，注明适用起点和失效条件 | 防止候选被当成成功技能；一例成功仍不代表任意位置通用 |
| 常规步骤与疑难步骤使用不同预算 | 日常已确认动作可试 low；图像矛盾、反复无进展、抓取/投放边界按规则升级 | 可能省预算；升级机制漏报与所有额外请求都必须统计 |

这里优先考虑的是让小预算模型接到明确、短小、可核对的问题。不是要求它面对同样长的上下文，关掉 thinking 后仍表现不变。

### 13.3 视觉弱时，单加文字推理可能不够

如果仍无法稳定辨认实体夹指、球和箱沿，就要改善视觉证据。例如保留全图的同时提供夹口附近的局部图，或以后考虑真机 RGB 也可运行的检测、跟踪与关键点模型。图像裁剪仍需要知道关注哪里，也可能丢掉全局关系；额外感知模型也可能误检。

“没有仿真真值”与“完全不能加工相机图像”不是同一限制。前者是迁移真机的原则；后者是我们当前更严格的实验边界。如果以后加入程序检测，应当作为明确的新实验方案单独比较，不能悄悄把检测坐标或仿真测距塞进当前 brain。这份文档没有实施这种改变。

还可以考虑在真机上真实获得的初始化或一次校准是否允许跨任务复用。现在每集清空全部经验，会强迫模型重复认识同一台机器；如果机器人、相机和动作接口稳定，把经过验证的经验作为独立技能保存可能更经济。前提是明确校准来源、适用条件和复验方式，不能使用模拟器独有的隐藏参数。

## 14. LangGraph 究竟是不是一个 if/else

**就当前阶段分派而言，是，可以用一个 phase 的 if/else 或字典分派实现。** 三个节点都调用同一个 `_plan`，没有三个不同专家，也没有自动的多智能体讨论。

**整个 brain 又不只是一段阶段判断。** 它还做当前图独立观察、参考图选择、跨轮状态保存、动作历史绑定、失败反馈、释放检查和日志记录。这些都是我们自己实现的程序功能，可以用普通 Python 保留，并不依赖“节点多”才能存在。

LangGraph 给的是有状态工作流的执行与持久化基础设施。它不会替开发者设计正确的状态或感知策略；这是官方对框架定位也明确区分的事情。[LangGraph 官方概述](https://docs.langchain.com/oss/python/langgraph/overview)

因此应该问：“保留这些记忆与检查，是否比没有它们更少失败、更省 token？”而不是只问“用了 LangGraph 有没有变聪明”。若普通 Python 用同样状态、同样模型调用就能达到同样效果，那说明收益来自设计，而不是框架名字。这完全可以是一个有效工程结论。

`langgraph_policy.py` 目前放阶段目标、提示词和输出协议；`langgraph_brain.py` 负责调用、状态和检查；`langgraph_memory.py` 负责存储。policy 不是另一个学习模型，也不是后续 ACT 策略网络。分开文件有利于分别审阅语言约定和执行逻辑，但不能掩盖提示已经过长的问题。

## 15. 下一次实验怎样才能回答问题，而不是再花一大笔钱

建议按以下顺序讨论和批准，不一次把所有部件都换掉：

1. **先排除已知文字混淆。** 两个 brain 的工具语义应一致，不能让 baseline 仍看到错误的固定肩方向说明；保留已验证代码快照。
2. **做不调用 API 的检查。** 对提示长度、图片选择、状态大小、已有回复的协议处理作离线核对。它们能检查程序，不能证明 low 的视觉效果。
3. **经批准后，拿少量具体难例比较模型。** 例如实体与影子、肩动作前后变化、抓空后的修正、箱沿遮挡。比较 high/low/disabled 的可见判断，而不只比较回答是否完整。复用历史图片向 API 重放需要另行批准；本次没有发送。
4. **选择一个最小改动做成对 GUI 测试。** 相同初始条件、动作接口、轮数上限与记录方式，明确此次只改变了哪个因素。若测试自适应升级，把升级请求也计入成本。
5. **先筛查，再扩展到预先约定的种子与重复次数。** 一次成功只能说明可行。要同时看入箱成功率、请求数、token、实际耗时、重复无效动作，以及生成轨迹中有多少时间在调试和恢复。

如果目的是收集 ACT 数据，教师每步都长时间思考并非最终目标。要比较“获得一条可用于训练的成功轨迹”到底消耗多少资源；成功轨迹中的长时间探索和反复抓空，也不能未经筛选就当成理想示范。当前项目尚未实现 ACT 导出与训练，这份文档没有补上那一部分。

我更倾向先整理现有提示和记忆分工，再测试 low，必要时保留少量 high 处理困难事件。独立文字模型是一个值得比较的方案，尚不是已证实的缺失环节；“全 disabled 也稳定完成”仍然是待验证目标。

## 16. Git 中怎样只把最终成果放进 main

当前分支名是 `goal_langgraph`，不是 `langgraph_goal`。相对合并前的 main（`6a7d37d`），它共有 28 个提交。

应把这 28 次修改累积后的最终文件状态做 **squash**，在 main 上生成一个新提交。只 cherry-pick 最后一个 `cdd5d2f` 不行：那个提交只是修复保存新参考时的一处状态判断，不包含之前建立的整个 brain。
