# 描述（人类）

数据库是否有 reach 图的信息：没有就 reach（stage 1）拍张照、然后 stow（stage 2）共计两步。（最高优先级）

根据历史信息看自己是否持球，三种状态：否、有待判定、是。由于是三个大类因此下面我们会说明每个状态的分支。

### 否

开启寻球。寻球时如果看不到球就**申请**右转信息，然后右转。

如果看得到球，先定位一个最近的球（路径上没有障碍），如果在匹配范围外就靠近（可能**申请**左右转和前进信息），在匹配范围内则用 reach+carry 组合，进入“有待判定”阶段。判断是否在匹配范围内**申请** reach 图。

### 有待判定

进行 reach（stage 1），然后和上一张对比，根据结果 stow 或 carry（stage 2）。

### 是

开启寻箱。寻箱看不到箱子就**申请**右转信息，然后右转。

看到了箱子，如果箱子和自己距离相当近（判定要**申请** reach 图）就 drop 然后进入“最终检查”。如果还有距离就靠近（可能**申请**左右转和前进信息）。

### 最终检查

一张图片，判断球是否在箱子里（理论上是能看到箱子里的全貌的，不会被遮挡住）。

### 数据库

数据库的作用：不是 langgraph 的数据库，而是我们构建关于操作本身的时间和空间直觉而使用的存储数据的 tool。具体来说，我们在上述每个阶段的 LLM 操作时，我们首先给到 LLM 的只有抽象概况，当 LLM 希望获取更详细信息时我们调用数据库上下文提供更详细信息。

也即，LLM 涉及到的操作会进一步调用数据库信息（然后重复，可以体现在状态中的一个比特表示是否具有**最终操作权限**，`0` 表示需要申请一些操作的更详细信息；`1` 表示已经看到了相关的信息有权进行操作）。

如果 LLM 调用数据库时数据库对应空的信息，就让数据库直接只进行对应操作，然后立刻结束，下面会自动载入相关数据。

每一轮维护上一张图 `→` 经过的操作 `→` 当前的图，如果中间经过的操作是纯的（即只有某种单独的操作，例如前进、转向）则可以载入数据库。

数据库存储三种类型的数据：**reach 图；前进后退；左转右转**。每种类型的数据保留 `≤2` 个样本。reach 图的样本是【一张 reach 状态的图片 + LLM 看图对“球的可抓取范围”分析】；前进后退和左转右转的样本是【上一张图 + 操作 + 这一张图 + LLM 的数据分析】。

在没有数据时首次操作会收集对应数据，通常尽量整体单位小一些且有参照物。

### 一些设计原则

LangGraph 状态节点：

- **起源**（是否开始新的一轮，每次开启新的一轮都需要先 stow。数据库是否有 reach 图，如果没有需要 reach 一次获取）。
- **“否”（持球）**：判定图中是否有球。没有球则申请/执行右转（但是没有参照物，可能没什么用，是否保留？）。有球则定位最近的球，申请 reach 图信息来判定是否在“可抓取”匹配范围内，不在则申请左右转和前进来靠近；在则进行 catch+carry 然后进入“有待判定”阶段。
- **有待判定**：即 reach，LLM 把上一次的 carry 时的图片拿出来对比看看是否架子上额外出现了球。根据结果决定进入“否”（持球）阶段（则 stow）还是“是”（持球）阶段（则 carry）。
- **“是”（持球）**：基本一致，判定图中是否有箱子，靠近，然后如果足够近则 drop（这里应该可以省略？）。
- **最终检查**：根据当前图片判断球是否在箱子里。如果都进入这个阶段还有问题的话直接抛出异常吧。

是否开始新的一轮可以用 `0/1` 表示（默认 `0`）。需要一个权限比特 `0/1` 类似于热水机的儿童锁一样。然后五个阶段对应不同的 LangGraph 阶段，这个在数据库里存好的。

**upd 来自 gpt6 Astra xhigh 补充：** catch / drop 需要包含夹爪开合，这一点已由用户确认。现有 `arm_pose` 只改变臂姿态，因此抓取组合补全为 `张爪 → reach → 闭爪 → carry`；投放补全为 `drop → 张爪`。“有待判定”中的 `reach` 是观察步骤，期间保持夹爪闭合，不通过松开可能抓住的球来检查是否持球。

# 描述（AI）

这是新实现遵循的设计。代码位于 `brains/langgraph/`，旧代码已归档，不沿用旧的探索、肩肘往返学习和 checkpoint 图片库。

核心：**五个任务阶段 + 一个按需申请的操作经验库 + 一次操作的权限位。** 每个阶段只回答自己的小问题；缺资料就申请，缺样本就试一次，动作后必须等新图。

## 1. 先明确两处用词

夹爪开合按上面的补充整理；“新的一轮”的范围暂按以下解释，尚未据此实现动作：

- **新的一轮**指一次完整的捡球投箱任务，不是每次 LLM 请求或每次取得新图。新任务先 `stow`，之后保持阶段进度。
- **catch / drop 是流程简称**。现有 `arm_pose` 只改变肩肘，不操作夹爪。抓取组合展开为 `张爪 → reach → 闭爪 → carry`；投放展开为 `drop → 张爪`。两者使用的仍是现有基础工具；待判定时的 `reach` 不张爪。

`reach` 图只能作为抓取范围和接近尺度的参照，不能单独证明球已经抓住或已经位于箱口内。

## 2. 五个 LangGraph 阶段

```text
起源 → 否 → 有待判定 → 是 → 最终检查 → 完成
         ↑      │
         └─ 未持球 ┘
```

寻球、靠近、寻箱都在所属阶段内循环。数据库申请与采样是共享流程，不增加第六个任务阶段。

| 阶段 | 本阶段只判断什么 | 资料与动作 | 下一阶段 |
| --- | --- | --- | --- |
| 起源 | 新任务是否初始化、reach 资料是否存在？ | 新任务先 `stow`。缺 reach 资料：stage 1 执行 `reach`；下次新图分析抓取范围并入库，stage 2 执行 `stow`。已有则跳过采样 | 否 |
| 否 | 有球吗？选中的球在可抓范围内吗？ | 无球：申请右转经验，再右转。有球：选当前可见、路径较空的最近目标；申请 reach 资料判断匹配。未匹配则申请所需移动经验并靠近；匹配则执行抓取组合 | 抓取后进入有待判定；否则留在否 |
| 有待判定 | 爪上是否确实有球？ | 保存刚才 `carry` 后的图；stage 1 执行 `reach`；下次新图与该 carry 图比较。stage 2：明确无球则 `stow`，明确持球则 `carry` | 否或是；仍看不清则回 `carry` 并保持有待判定 |
| 是 | 有箱子吗？是否已经接近投放位置？ | 无箱：申请右转经验，再右转。有箱：申请 reach 资料辅助判断远近；不够近则申请移动经验靠近。具备投放条件后执行投放组合 | 投放后进入最终检查；否则留在是 |
| 最终检查 | 当前图中球是否在箱内？ | 只检查释放后的当前图 | 是则完成；否或无法判断则抛出异常，保留现场，不自动重试 |

reach 资料是启动后的最高优先级，补齐前不进入寻球。每个 stage 之间隔着真实动作和下一张新图；不能在一次模型回复里假装已经完成观察。

补齐 reach 资料指保存原图与分析，分析可以明确“不确定”；不要求初始化时一定生成可靠的数值区域。保存后先回 `stow`，能否匹配由后续模块根据原图和当前目标判断。

“有待判定”的两图姿态不同，比较对象是球与实体夹指的夹持关系；不能只因画面里多出一颗球就认定抓住。看不清不强行归入“否”或“是”。

## 3. 请求资料与操作权限

每次进入阶段，先给模型：**当前图、阶段/目标/持球概况、数据库目录摘要**。目录只说明有什么资料，不默认附上全部历史图片和分析。

模型只需要两类输出：

- `request_info(kind, direction?)`：申请 reach、前后移动或左右转向的详细资料。
- `submit_action(...)`：根据已经看过的资料，提交本阶段允许的动作。

程序控制权限位 `can_act`，模型不能自行将它改成 `1`：

```text
can_act = 0
    → 申请资料
    → 命中：把详细样本送入上下文，再让模型判断
        → 当前操作所需资料齐全：can_act = 1 → 可提交本次动作
        → 还缺其他资料：继续申请
    → 未命中：只触发一次对应试探 → 立即结束当前决策
        → 执行 → 新图 → 分析并入库 → 回原阶段重新申请/载入
```

权限绑定当前图片、目标、阶段和待执行的操作；执行动作或改变目标/阶段后重置为 `0`。读过右转资料不等于获得前进许可。固定初始化步骤与数据库触发的单次试探由程序执行，不借此开放任意动作。

数据库工具负责触发试探，底层仍统一执行现有机器人工具；同一次未命中请求不能再附带抓取、投放或其他正式动作。资料申请可以在同一张当前图上重复，动作后的判断必须等新图。

实现中的调用优化：首次找目标仍只给概况；确定进入匹配后，程序代为申请必需的 reach 资料，刚从纯动作学到的那份运动资料也直接给规划模块，减少重复询问。其他资料继续按需申请，权限仍绑定当前帧与实际动作；重复索取已给资料时明确告知没有更多样本，允许返回不确定。

## 4. 操作经验库

它是供模型申请的**操作资料工具**，与 LangGraph 的任务进度存储分开。初期可用普通文件或 SQLite 实现，不要求使用 LangGraph checkpointer。

| 类别 | 一个样本包含什么 | 容量与保留办法 |
| --- | --- | --- |
| reach | reach 状态原图 + 模型分析的球心可抓范围及未知处 | ≤2；保留当前配置下有效的参考，新分析不能覆盖掉其原图 |
| 前进后退 | 前图 + 实际动作及秒数 + 后图 + 同一参照物的变化分析 | 合计 ≤2；优先前进、后退各一条有效样本，同方向用较新的有效样本替换 |
| 左转右转 | 前图 + 实际动作及秒数 + 后图 + 同一参照物的变化分析 | 合计 ≤2；优先左转、右转各一条有效样本，同方向用较新的有效样本替换 |

某类非空但没有所申请方向的有效样本，仍视为该方向未命中；不能把右转样本自动当作左转样本。

程序每次取图维护 `上一张图 → 实际经过的操作 → 当前图`。只把纯动作段写入运动经验库：

- 全段只有同一种底盘动作，例如只有 `forward`；前进加转向、前进加后退、同时调臂都不作为纯动作样本。
- 前后能对应同一静止参照物；图片没有明显变化，也可以如实记录。
- 原图和实际指令由程序绑定，模型只分析可见效果，不编造距离、速度或转角。
- 首次试探采用配置好的较小时间单位，优先保留参照物；取得后图后才能生成完整样本。

**没有参照物的右转仍可用于搜索，但不计入有效运动样本。** 下次继续缺资料时仍可小步搜索，不因数据库为空卡死；一旦出现可比较的前后图再入库。

每类最多两条指供模型使用的有效样本；普通执行日志可单独记录失败，不混入这个小经验库。新任务重置阶段，不清空有效经验；机械臂、相机或控制配置改变后，相关样本重新验证。

## 5. 最小任务状态

| 字段 | 含义 |
| --- | --- |
| `phase` | 起源 / 否 / 有待判定 / 是 / 最终检查 |
| `started` | 默认 `0`；本任务起始 `stow` 执行后为 `1`；新任务重置为 `0` |
| `step` | 所属阶段的进度，区分 stage 1 动作已发出、等待新图、stage 2 待执行 |
| `can_act` | `0/1`，当前这次操作的权限 |
| `request` | 当前申请的资料种类、方向和待完成操作 |
| `target` | 当前选中的球或箱子；遮挡时先保留身份，不随意换目标 |
| `last_transition` | 前图、实际动作、当前图的引用，用于纯动作采样 |
| `carry_frame` | 待判定阶段要比较的那张 carry 图，不能被其他取图覆盖 |

这些字段属于运行状态，可另外保存以恢复任务；五个节点及转移规则定义在图里，不当作操作经验样本塞进数据库。

## 6. 实现前保留的两点边界

1. **drop 能否省略**：默认先保留投放姿态转换。只有当前姿态本来就能完成投放时才可省去重复的 `drop`；释放球所需的张爪不能省。接近程度可参考 reach 图，但投放条件仍要看当前球与箱口的关系。
2. **最终检查的视野前提**：按原文先采用“一张图能够看清箱内”的假设。如果实际看不清，也按最终检查失败抛出异常，不新增一套恢复流程。

每个阶段使用一句任务说明和固定输出格式；数据库返回的是少量相关原图与分析。先实现并检验这条流程，不再引入旧版肩肘探索、长篇历史总结或额外任务阶段。

## 7. 可替换的模块架构

目标是**用尽量低的成本采集有效数据**。五个阶段保持稳定；每个具体判断可以独立更换模型、prompt，或替换成普通程序。以下保留架构构想；实际文件说明和运行方法见 [langgraph/README.md](langgraph/README.md)。

### 7.1 图负责流程，小模块负责判断

建议按职责组织，不要求每个函数都单独建文件：

```text
brains/langgraph/
  brain.py          接入现有 Brain 接口，每次接收新图并推进任务
  graph.py          五个阶段及转移规则
  stages.py         各阶段调用哪些小模块，何时申请资料、提交动作
  contracts.py      任务状态、各模块的输入输出格式
  capabilities/     找目标、范围匹配、持球检查等小任务
  prompts/          每个小任务自己的短 prompt
  backends/         模型调用适配；以后按需加入视觉算法或规则实现
  memory.py         三类操作经验的查询、筛选与存储
  execution.py      权限检查、组合动作展开、对接现有执行器
  profiles.yaml     按小任务选择实现、模型和 prompt
```

**一个 LangGraph 节点不等于一次大模型调用。** 节点主要是普通代码；只有当前分支需要的判断才调用对应模块。起源的固定步骤不需要模型规划，寻球也不必运行寻箱和最终检查模块。

小模块只返回结果，不直接改阶段、写经验库或操作机器人。状态与 `can_act` 由流程代码更新；实际动作仍交给现有执行器，取到新图后才继续。第 3 节的资料申请/动作提交是阶段对外协议，下面的小模块结果属于阶段内部。

### 7.2 按小问题划分能力接口

| 模块 | 最小输入 | 返回什么 |
| --- | --- | --- |
| `find_ball` | 当前图、已有目标编号（如有） | 可见球的位置、目标候选及可见路径情况；找不到或看不清 |
| `find_box` | 当前图、目标箱信息 | 箱口的位置；找不到或看不清 |
| `match_grasp` | 当前球的位置、当前图、申请到的 reach 参考 | 匹配 / 不匹配 / 不确定 |
| `plan_motion` | 搜索或靠近的意图、目标信息、当前图、所需方向的运动经验 | 一个底盘动作及持续时间，或缺少的资料 |
| `check_held` | 指定的 carry 图、随后取得的 reach 图 | 持球 / 未持球 / 不确定 |
| `match_drop` | 当前球与夹指、箱口的信息及图像、申请到的 reach 参考 | 可以投放 / 还需靠近或调整 / 不确定 |
| `check_drop` | 释放后的当前图、目标箱信息 | 球在箱内 / 不在箱内 / 不确定 |
| `analyze_reach` | reach 图、相机与姿态配置标识 | 球心可抓区域及未知处 |
| `analyze_motion` | 前图、实际纯动作及时间、后图 | 参照物变化、分析及是否适合作为经验样本 |

这些是职责边界，不是每轮都要串行调用的清单。同一张图上已有的有效定位结果可以复用；以后若增加专用目标检测器，再把定位部分抽出来共享，不先强制增加一轮“完整场景描述”。

### 7.3 每个小任务拥有自己的 prompt 和上下文

每个模块分别配置 **实现方式、模型、prompt 文件、输出长度上限**。超时、重试等通用逻辑由调用适配器处理；它不附加整套机器人任务的长 prompt。

例如两段 prompt 可以短到：

```text
match_grasp：判断指定球心是否落入给定抓取区域。返回匹配、不匹配或不确定。
check_held：比较 carry 图与 reach 图，判断夹指是否实际夹住球。看不清则返回不确定。
```

对象编号、坐标约定和输出 schema 由结构化输入提供，不在自然语言中反复解释。每个模块只收到所需字段、指定图片和已申请的相关样本；不给它整个任务历史、其他阶段的 prompt 或完整数据库。

同一个模型也使用各自的短 prompt；简单判断和复杂两图判断可以使用不同模型。是否采用更强模型，以该模块的实测错误率决定，不默认所有模块都调用两遍。若配置升级模型的后备方案，应有明确触发条件和次数上限。

### 7.4 替换实现，不改变流程语义

接口首先表达任务，例如 `match_grasp(input) → result`，而不是把所有模块都做成 `chat(messages)`。每个接口有自己的固定字段；LLM、视觉算法、普通规则都适配同一接口。阶段代码通过配置拿到实现，不判断具体模型名称。

例如，把 `match_grasp` 从模型换成程序：

1. 保留输入中的目标球心、抓取区域、图片编号和配置标识。
2. 程序在相机、姿态及坐标约定一致时，计算球心是否落入区域。
3. 仍返回相同的三态结果，寻球节点及后续抓取流程不变。

这里需要有效的球心定位与区域标定；缺失时返回不确定，不能假定程序天然看得懂原图。范围匹配也仍只是抓取前的条件，不能替代抓取后的持球检查。

结果必须绑定输入图片和目标；`不确定`、`缺资料`、`调用失败` 分开表示，不能都当作“否”。缺资料继续走第 3 节申请流程；更换为程序实现也不能绕过资料有效性检查和动作权限。模型故障由适配器有限重试，耗尽后明确报错，不伪装成视觉结论。

### 7.5 为低成本采集保留可比较的数据

除三类小经验库外，单独记录每次模块调用的**输入引用、结构化结果、实现/模型/prompt 版本、耗时、token 用量及后续执行结果**。日志不自动塞进下一次 prompt，也不受经验库每类两条的限制。

这样可以拿同一组保存的图片，单独重放 `check_held` 或 `match_grasp`，比较短 prompt、小模型与程序规则，无需每换一次模型就重跑机械臂。离线比较使用人工核对过的标签；机器人实际抓取、投放结果用于检查整条流程，大模型的回答本身不当作标准答案。

复用结果必须限定在相同输入、模块及配置版本内；新图、目标变化或实现变更后重新判断。成本既看调用次数、图片数和 token，也看**每条有效采集数据的总成本与失败率**，避免单次便宜却反复抓空。

实现顺序建议：先定小接口和五阶段调度，再接入各自的短 prompt，保存少量可重放样例；之后逐个替换模型或加入规则实现。初期用普通 Python 函数、配置表和依赖传入即可，不需要复杂插件框架。
