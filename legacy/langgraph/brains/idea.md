### idea（人类语言）

我觉得最重要的是我们需要构建一个可检验的替换方案，我们前面的 prompt 之所以笨蛋就是因为，我们其实不知道某一次改进的效果如何，每次就像抽奖一样，我们没有一个很好的检验标准。

那么接下来我们就应该把整个步骤切开（为了之后支持非 reasoning 模式），例如第一个模块是把图片转成字符画，要求模型对图片的每个主体有边界的识别能力，这个是可以量化检验的，即我们把前面的一些车载图片提取出来然后类似算法竞赛搭建可检验的一个基于测试点的系统，便可以知晓 reasoning 和非 reasoning 的差距。

然后比如说我们把整个活动分解成三到五个节点，就是我们前面 langgraph 想做的事情。我们可以把字符画取出来，然后让模型来根据字符画判断我们当前的阶段和进展。如果当前阶段比较有歧义（例如只有七成把握，或者在试图判定是否抓住了球）我们就取出历史记录甚至是前面的图片再进一步判断。

然后为了让所有的阶段的边界足够明确，我们要求不能把靠近到球的附近和捡球合并在一起。

但是这样下面的内容就有一个问题，就是，我们如何量化检验，我们可以这样，先让 reasoning 做每一个阶段，然后把非 reasoning 对每个阶段单独提取出来，把所有数据用于测试准确率。

以及我们可以让模型进行想象，例如当模型锁定了一个球之后，我们可以把这个球在图片的字符画里标注出来，然后，想象，以及如果我们已经探索好了基础的抓球动作，我们可以在字符画中标注一个区域，只有球和这个区域的匹配程度较高时才有可能抓球。对，我觉得搭建一个，我不希望是一个没有可检验标准的 workflow，那样效率很低而且非常糟糕，我们希望把每个阶段都切分的足够小，然后首先让 reasoning 能跑起来（而且 prompt 尽可能短），然后，这个时候的 workflow 才是有意义的，即我们的模型需要什么我们再在这个 langgraph 中调用什么，然后相当于一个循环作用。

### idea（AI 语言）

我对这段想法的理解是：建立一个可以分模块检验、逐步替换模型的机器人数据采集系统。先用 reasoning 模式跑通职责明确的小模块，再通过固定测试点，判断哪些模块可以由非 reasoning 模式或更便宜的模型承担。每次修改 prompt、表示方法或模型配置，都应有可重复的对照结果。最终目标是降低每条合格机器人示范的时间、费用和人工成本，为 ACT 提供可用的训练数据，并支持真机采集。

以下是对这一方向的具体化理解；节点划分、格式和阈值属于待验证的设计，不代表已经实现或证明有效。

1. **先定义模块的输入、输出和判定标准。**

   第一个模块接收车载相机图像，输出带有物体类别、位置和边界的字符画。字符画应固定网格尺寸、坐标方向、符号图例、目标编号，以及遮挡和无法判断时的表示规则。球、实体夹爪、影子、地面、箱体及箱口等信息应能够区分。语法格式是否正确与视觉识别是否正确分别评分，避免把排版错误混同为识别错误。

   这一模块的产物是对可见证据的转录。二维重叠不能直接推出接触、抓住或离地；看不清的物体边界和物理关系应允许保留未知。字符画是否保留了后续决策所需的信息，也需要单独检验。

2. **把活动拆成具有明确入口、出口和失败条件的阶段。**

   可先讨论以下五个任务节点；视觉提取、历史检索和动作预测是按需调用的功能模块，不必各占一个任务阶段。

   | 候选节点 | 职责 | 进入下一阶段需要的证据 |
   | --- | --- | --- |
   | 探索与标定 | 验证基本抓球姿态、观察姿态及适用的往返动作 | 获得经过实际执行检查、适用条件明确的操作方法 |
   | 锁定目标与接近 | 选定并持续跟踪同一颗球，使其进入可做精细对准的范围 | 当前观察支持目标已进入下一阶段的工作范围；本阶段不执行抓取 |
   | 精细对准与抓取 | 比较目标与抓取区域，完成局部调整并发出抓取动作 | 抓取动作已执行；此时仍不能宣布抓取成功 |
   | 抓取验证 | 根据抓取前后观察和实际动作判断是否抓住、是否需要补充观察或重试 | 有足够证据确认持球，才允许进入搬运 |
   | 搬运与投放 | 持球接近箱子、检查释放条件、执行投放并确认结果 | 投放后的观察支持任务完成；不明确时继续检查或进入恢复流程 |

   每个节点内部继续拆成可独立测试的小判断。接近和抓取必须分开；发出了闭爪指令、观察到持球、确认任务完成也必须是不同状态。节点切换依赖证据，失败时应明确返回哪个节点。

3. **按需获取证据，形成有条件的循环。**

   先使用当前字符画和最小必要状态判断阶段与进展。只有证据不足、前后矛盾、目标身份不清或处于抓取确认等关键边界时，才补充相关动作记录、历史字符画或原始图片。补充证据后重新判断，再决定执行、继续观察或恢复。

   “七成把握”表达的是需要设置升级检查条件。模型口头报告的置信度不能直接当作真实正确率，阈值要在有标签的测试点上校准；也可以先使用可检查的条件，例如关键物体不可见、证据互相冲突或缺少动作后的观察。需要记录补充证据和调用 reasoning 的频率，判断是否仍符合成本目标。

4. **以固定测试点检验每次替换。**

   从已有运行记录和后续 reasoning 运行中提取阶段输入，保留原始图片、相关历史、已执行动作及前后结果，形成可重复运行的测试样本。覆盖成功、失败、遮挡、误认影子、多球混淆和阶段边界等情况，不只选择成功轨迹中的容易画面。

   reasoning 输出可以提供候选答案和案例，但不能直接视为标准答案。标签需要人工核对，或使用只服务于评估的仿真真值；对仅凭给定输入无法确定的情况，标准答案也应允许“无法判断”。仿真真值不得泄漏到计划部署到真机的模型输入中。

   固定样本、输入权限、输出格式和评分程序，比较 reasoning、非 reasoning 以及不同模型的结果。保留开发集和独立测试集，按 episode 或场景划分，避免相邻帧同时进入调参和最终测试。“使用所有数据”应理解为充分利用已有记录构建测试体系，同时保留没有被反复用于修改 prompt 的检验样本。

5. **分别定位感知、阶段判断、行动和预测的问题。**

   感知测试比较主体识别、边界或区域重合、目标位置误差，以及实体夹爪与影子的混淆；按类别评分，防止大面积地面掩盖关键物体错误。阶段测试比较状态识别、进展判断、切换时机和未知状态处理，重点检查“尚未抓住却宣布持球”等错误。

   对后续模块，分别输入人工核对的表示、reasoning 生成的表示和非 reasoning 生成的表示，尽量一次只改变一个因素。若人工核对的字符画仍无法支持正确决策，需要检查表示是否缺少必要信息或决策模块是否有问题；不能把全部错误归因于视觉提取。

   行动可能有多种正确选择，不应只按是否复现 reasoning 的同一条指令评分。应依据前置条件、允许的动作范围以及执行后的目标效果检验；需要比较不同动作结果时，应从相同起始状态执行短段闭环测试。

6. **让目标标记、抓取区域和“想象”成为可检验的对象。**

   锁定球后，在字符画中保持可追踪的目标编号，避免悄悄换成另一颗球。基础抓球动作验证后，可以标记与对应姿态及相机配置关联的候选抓取区域，明确目标与区域的匹配规则。区域匹配是允许尝试抓取的条件之一，不能替代抓取后的验证；姿态或观察条件变化后，要重新检查区域是否适用。

   “想象”可以具体化为：给定当前表示和候选动作，预测目标、夹爪或遮挡关系会怎样变化。执行后用真实的新观察检查预测误差，再决定是否继续或修正。预测结果必须与真实观察分开保存，不能用预测到的持球或投放成功推进阶段。

7. **先建立短 prompt 的 reasoning 基线，再逐个替换。**

   每个模块只接收完成其职责所需的信息，prompt 保留明确任务、输出约定和必要约束。先验证 reasoning 基线，再冻结测试条件，把某一个模块换成非 reasoning，比较准确性、关键错误率、请求次数、tokens、耗时及升级检查率。通过模块测试后，再做阶段闭环和完整任务测试。

   离线测试用于筛选方案；替换后的模型会产生新的动作和状态，因此仍需补充其实际运行中出现的失败样本。最终依据完整闭环中的合格示范比例、每条合格示范的总成本和每小时产量，判断替换是否成功。

8. **让测试体系服务于真实采集和 ACT。**

   LangGraph 负责按当前状态调度所需模块、维护证据和控制阶段切换。每个节点是否必要、每次增加复杂度是否有效，都由测试结果说明。采集仍需保存同步的原始相机图像、本体状态和实际控制指令；字符画、阶段标签及预测作为附加记录，用于诊断和比较。通过明确的数据质量标准筛选示范，再连接 ACT 训练和执行验证，最后检查同样的输入和控制接口在真机上是否可用。
